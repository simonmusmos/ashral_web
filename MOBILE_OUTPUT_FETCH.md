# Mobile Output Fetch Guide

This backend stores terminal output as ordered chunks under a session.

For a mobile app, the read path is:

1. Create or obtain a `sessionId`
2. Join the session if you want the user associated with it
3. Poll `GET /sessions/:id/output`
4. Merge chunks by `chunkId` on the client

## Base URL

- Local: `http://localhost:3000`
- Production: `https://<your-vercel-project>.vercel.app`

## Output model

Each output item returned by the API has this shape:

```json
{
  "chunkId": "c2fd4a8e-7db9-4ca8-8f2a-d7f6f2e01d88",
  "seq": 42,
  "text": "Running tests...\n",
  "stream": "stdout",
  "messageId": null,
  "part": null,
  "parts": null,
  "createdAt": { "_seconds": 1712412345, "_nanoseconds": 123000000 }
}
```

Fields:

- `chunkId`: unique ID for the chunk (generated by the CLI, so retries never duplicate)
- `seq`: per-session order, assigned by the backend. `null` on chunks written before seq existed
- `text`: message text
- `stream`: `stdout` = agent output, `stderr` = user message
- `messageId` / `part` / `parts`: set only when one message (> 100k chars) was split; append parts with the same `messageId` in order
- `createdAt`: Firestore timestamp object

## Fetch output

```http
GET /sessions/:sessionId/output?limit=200              # latest 200 chunks (initial load)
GET /sessions/:sessionId/output?afterSeq=42&limit=200  # only chunks with seq > 42
```

Response:

```json
{ "chunks": [ ... ], "lastSeq": 57, "hasMore": false }
```

- Chunks are always returned oldest first
- `lastSeq` is the cursor to send as `afterSeq` on the next request
- `hasMore: true` means the page was full — request again straight away
- `limit` defaults to `200`, max `1000`
- `404` if the session does not exist

## Recommended mobile strategy

1. Initial load: `GET /output?limit=1000` (no `afterSeq`)
2. Then poll every `2-5s` with `afterSeq=<lastSeq>`, repeating while `hasMore`
3. Dedupe by `chunkId` (cheap safety net for overlapping polls)

File diffs work the same way: `GET /sessions/:id/diffs?since=<epoch ms>` returns diffs created at or after that time; dedupe by `toolUseId`.

## Sending messages to the CLI

`POST /sessions/:id/respond` and `POST /sessions/:id/respond-image` append to a per-session inbox (`sessions/{id}/inbox`). The CLI pops one entry per `GET /sessions/:id/response`, oldest first, so messages sent in quick succession are all delivered, in order.

## Recommended companion calls

Use these endpoints with output polling:

### Create session

```http
POST /sessions
Content-Type: application/json
```

```json
{
  "agent": "codex",
  "name": "Fix login screen"
}
```

Response:

```json
{
  "sessionId": "SESSION_ID"
}
```

### Join session

```http
POST /sessions/:sessionId/join
Content-Type: application/json
```

```json
{
  "userId": "firebase-user-id",
  "customName": "Simon"
}
```

### Read session list for a user

```http
GET /users/:userId/sessions
```

This is useful if the mobile app shows recent or active sessions.

## Status checks

Read `status` and `pendingAction` from `GET /sessions/:id`.

Session statuses used by the backend: `active`, `waiting_for_input`, `running`, `completed`, `error`, `terminated`.

## Current limitations

- No authentication is enforced on these routes
- No server-sent events or websocket stream — clients poll
